## 2. Demo skin integrity

`BodySurfaceTest` builds the real demo scene, then checks the skinned body:

- 10,800 vertices, 10,798 quads (~21.6k triangles)
- exactly one connected component
- 0 open boundary edges
- 0 non-manifold edges
- every directed edge used once (consistent winding)
- positive signed volume
- no NaN vertices
- bounds consistent with a 1.8 m humanoid
- body build + skinning: ~250–350 ms on the JVM test host

The skin is generated by `ImplicitSurface` (SDF primitives + surface nets + two Laplacian passes), not by intersecting primitive shells. This removed the dark sawtooth fringes that appeared at the shoulders, waist, elbows and knees in the previous build.

Runtime load with three.js (`build/qa/runtime_load.mjs`): **OK**.

The validator pass found and we fixed one real defect: zero-weight skin influences were exporting a leftover joint index, producing `ACCESSOR_JOINTS_USED_ZERO_WEIGHT`. The exporter now writes joint 0 for zero-weight slots. This reduced 991 warnings to 0.

A second earlier fix (already in this build) declared `KHR_materials_emissive_strength` in `extensionsUsed` and corrected inverse-bind-matrix homogeneous rows.

## 5. Physical-device pass (release build)

Performed on a Redmi phone (1080×2400, Android 15) with the signed release APK, fresh install (`pm clear` first):

- App info shows the new adaptive icon; cold launch shows the branded splash, then the ink loading surface, with no white flash or theme jump.
- First-run tour renders all three pages (cube, rig, export). Continue, Skip, “Explore the ATLAS demo” and “Start with an empty scene” all navigate for real; the choice persists through process death.
- The empty-scene start produces a blank grid scene (“Untitled Scene”, 0 tris) that can be built on.
- The demo start builds ATLAS (24-bone rig, 41K triangles in the HUD) and holds **60 FPS** at the default camera on hardware GL.
- Object → Model → Rig → Animate switching works; tapping the chest in Model selects “Chest Inset”, tapping it in Rig selects “Chest”, and Animate shows the timeline with per-bone key rows.
- Settings: light, dark and system themes switch immediately; canvas and workflow toggles persist; About opens the real build sheet (version, what’s new, engine facts, privacy).
- Autosave and undo operate during the edit session; the animated demo plays without NaN/distorted skinning.
- Top-bar menu, import sheet and export sheet open and lay out correctly at 1080×2400 with edge-to-edge insets.

The earlier emulator pass (540×1200 logical, software GL) still reports 3–9 FPS, which is expected without GPU acceleration and is not a product signal. Its file-picker limitation is superseded by the physical-device pass for UI layout, but higher-level save to Downloads was not automated.

Screenshots from this pass: `docs/store/raw/` (raw) and `docs/store/screenshots/` (store cards).

## 6. Performance

| Device | Scene | Result |
|---|---|---|
| Emulator, software GL | 28k triangles, 24-bone skin | 3–9 FPS |
| Physical Redmi (earlier build) | 11k triangles, 24-bone skin | 60 FPS |
| Physical Redmi, **current mesh** | 41k triangles in HUD, 24-bone skin | **59–60 FPS** at the default camera |
| Physical Redmi, Animate with timeline | 41k triangles, timeline compositing | 52–60 FPS |

Frame rate was read from the in-app HUD while orbiting and playing the demo clips. The emulator has no GPU acceleration, so its numbers are not a product signal.

Cold start on the emulator was 15.6 s for the R8 release build from a clean launcher state; the physical phone reaches the loading surface almost immediately, and the first usable frame arrives after the demo is built. A precise physical cold-start timestamp was not captured with a profiler, so treat launch latency as “subjective, under the loading screen” rather than a measured number. If it becomes an issue, prebuild the demo mesh or reduce the SDF cell resolution (currently 0.0185 m, 10.8k vertices).

Memory: the release process stayed under ~40 MB Java heap during startup. The SDF evaluation uses allocation-free scalar math to avoid GC churn.

## 7. Remaining risks

1. **FBX unsupported.** UI discloses it; no dummy controls.
2. **glTF material subset.** Normal/ORM maps and morph targets are absent.
3. **48-bone cap.** Enforced by the shader uniform array; larger rigs need a different skinning path.
4. **No libf3d.** The renderer is a custom Kotlin/OpenGL engine (see README).
5. **No automated UI/instrumentation tests.** UI checks were manual; the engine has strong unit coverage but Compose flows are not regression-tested.
6. **Store media is hardware-specific.** Screenshots were captured on a 1080×2400 Redmi; tablet screenshots and a promo video are still optional gaps.
7. **Physical cold-start timing is not profiler-measured.** The loading surface covers scene construction; no ANR was observed.
